## 1. 本方针决定什么

本文件只决定四件事：

- 三条路线的长期主次关系；
- 阶段之间的静态依赖和切换规则；
- 新任务能否进入执行面的准入规则；
- Agent 在文档冲突、阻塞和用户临时指令下如何行动。

本文件不承担：

- 动态记录每个任务完成到哪一步；
- 复制 WORKPLAN 中的施工细节；
- 复制实验协议中的条件、指标和统计方法；
- 代替代码、数据库或真实运行结果说明“现在已经实现了什么”。

因此，**完成任务不修改本文件**。进度只更新 HANDOFF；已有 WORKPLAN 条目完成后，按现行规则从 WORKPLAN 删除或归档，但不得向 WORKPLAN 增长新任务。

## 2. 文档权威分层

### 2.1 执行顺序与授权

| 优先级 | 来源 | 能决定什么 | 不能决定什么 |
|---|---|---|---|
| 1 | 用户当前明确指令 | 当前窗口范围；明确的一次性插队；明确批准修改长期方针 | 仅提到一个想法，不自动等于排期 |
| 2 | 本文件 | 长期主次、交替节奏、营销闸门、任务准入、变更控制 | 具体实现细节和动态进度 |
| 3 | 首屏明确 active、未标 SUPERSEDED、取代关系最新的 HANDOFF | 当前现场、唯一下一步、阻断、新发现、小功能队列、验收回执 | 改写长期战略或让新发现自动插队 |
| 4 | docs/WORKPLAN-2026-08-22.md | 已有 backlog 的施工细节、依赖、红线和历史理由 | 继续增长新任务；覆盖更新后的 HANDOFF 或本方针 |
| 5 | 设计稿与实验协议 | 解释候选功能、研究边界、实验方法和停止条件 | 单独授权实现、发布或营销声明 |
| 6 | PLAN_EN.md | 产品宪法、核心原则、历史否决的参考 | 当前状态、schema、版本、LICENSE、当前排序 |

本方针建立后，旧文档中的“C 批可以随时插入”“渠道必须把 R2 做完才进入 E”等表述，不再拥有执行权。保留它们是为了历史依据，不是为了重新开工。

### 2.2 事实权威与排序权威必须分开

- “现在代码怎么运行”以当前代码、schema、测试和实际运行结果为准。
- “现在做什么”以本文件加最新 HANDOFF 为准。
- “产品红线是什么”以用户最新明确决定、当前 HANDOFF、WORKPLAN 红线和当前隐私文档为准。
- PLAN_EN 中仍有旧版本、旧 schema 和 MIT 等过期文字；只可引用仍被当前事实确认的产品原则。
- 对外数字必须重新测量。工具和 prompt 的 2026-08-26 快照是 22 / 7，但发布或宣传前仍要从实际二进制重数。
- 可披露数字以 raw artifact、运行 manifest、真实账单和 CASE_STUDY_LEDGER.md 为准；HANDOFF、设计稿和厂商自报数字都不能代替最终证据。
- archive 只供查历史理由，不是执行入口。

### 2.3 冲突处理算法

遇到两个文件不一致时，Agent 必须：

1. 先判断冲突是“事实”还是“执行顺序”；
2. 对事实查代码、最新运行记录或更新日期，不凭记忆选；
3. 对顺序按 §2.1 处理；
4. 若高层来源仍无法给出唯一答案，停止施工，把冲突和两种后果写入 HANDOFF，询问用户；
5. 不允许用“我认为更合理”静默覆盖。

## 3. 所有者锁与修改许可

### 3.1 什么才算允许修改本文件

以下表达才构成许可：

- “修改 docs/EXECUTION_POLICY.md 的……”
- “把总执行方针中的……改成……”
- “以后永久调整产品/研究/营销的顺序为……”
- 其他同等清楚、明确指向长期规则的指令。

以下都不构成许可：

- “continue”；
- “更新 handoff / 更新文档”；
- “做这个功能”；
- “把这次发现记下来”；
- “顺便保持计划一致”；
- Agent 自己认为现有顺序效率不高；
- 一次实验结果或一次竞品更新；
- 用户在讨论中提出可能性，但没有说现在排期或修改方针。

### 3.2 用户一次性插队不等于永久改方针

用户明确说“这件现在先做”时：

1. 在 HANDOFF 标为 owner interruption；
2. 执行该次任务；
3. 完成后回到被中断的原阶段；
4. 除非用户同时明确说永久重排，否则不修改本文件。

用户直接要求“做 X”已经授权本轮做 X，但若 X 与保护顺序冲突，只把它视为一次性 owner interruption；Agent 必须在 HANDOFF 写明返回点，不能据此移动后续阶段。

### 3.3 Agent 认为方针应该改变时

只能在 HANDOFF 写一条 policy change proposal，至少包含：

- 当前规则；
- 新证据；
- 建议变化；
- 会被推迟或取消的任务；
- 不改变会有什么代价；
- 状态：等待用户决定。

不得先改本文件再让用户审阅。

### 3.4 获得同意后的变更程序

只有明确同意后才可以：

1. 修改相应规则和版本号；
2. 在本文件末尾追加变更记录；
3. 同步最新 HANDOFF 的当前阶段；
4. 只在确有必要时更新 WORKPLAN 的已有条目；
5. 说明被移动任务和代价。

## 4. 三条路线的永久关系

| 路线 | 永久角色 | 方针状态 | 允许的工作 |
|---|---|---|---|
| P · 产品完善 | **永远的主线** | 默认返回路线 | UI/UX、可靠性、细节功能、分发入口、graph、事件/时间、音视频及未来被用户批准的产品任务 |
| MEM · AI 记忆研究 | **第二中心** | 按有界研究里程碑运行 | E1/E2、项目工作指南实验、跨模型/跨客户端评测、benchmark、论文和复现材料 |
| MKT · 营销商业 | 研究成果后的放大器 | 成果闸门和用户批准前不得有 dedicated work | 闸门前只收集自然产生的真实素材；闸门后仍需用户明确重开，才做品牌、视频、渠道、定价和发布 |

### 4.1 “产品永远主线”的操作定义

- 每份 HANDOFF 都必须保留一个明确的下一项产品里程碑。
- 研究结束、阻塞或预算不足时，立即回到产品，而不是等待研究条件变好。
- 产品没有“全部完成”的终局；v1.0 过渡图中的 F 批结束后，由用户在 HANDOFF 候选中批准下一项产品里程碑。
- 研究成果进入产品必须过协议中的 utility、harm、portability 和 approval burden 闸门；没有过门，不实现项目工作指南。
- 不能为了论文或宣传制造一个与真实产品分叉的“展示版 Spool”。

### 4.2 “记忆研究是第二中心”的操作定义

- 研究不是随手问几个模型，而是有 protocol、冻结条件、原始数据、失败记录、费用和限制的独立工作。
- 每个研究窗口只做一个可验证交付物，例如“冻结 v1.0”“完成 instrumentation pilot”“完成 Track A”，不能同时开完整论文、产品原型和跨客户端矩阵。
- confirmatory wave 冻结后，新变量、新题型和新条件只写 amendment 或进入下一 wave；不能中途改主指标。
- 实验运行期间若产品代码、adapter、模型、客户端或数据发生相关变化，先判断当前 wave 是否失效或必须拆成新 wave，不能无条件合并。
- 研究失败、FullText 获胜或竞品获胜都是有效结果，不得为了产品结论换题或删不利数据。

### 4.3 “营销只收素材”的操作定义

营销闸门开启前可以做：

- 保存开发自然产生的真实截图或原始录屏；
- 保存真实交互步骤、版本、commit、环境和日期；
- 保存失败、修复前后和用户真实反馈；
- 保存研究图表、原始结果路径及它不能证明什么；
- 在 HANDOFF 记录素材路径和授权状态；
- 把经过核对的数字写入 CASE_STUDY_LEDGER.md。

以下行为已经是独立营销任务，闸门前禁止：

- 为了好看重拍或搭建场景；
- 剪辑视频、写宣传文案、做海报或 Logo 细化；
- 制作 mock 冒充产品；
- 发布社媒、Show HN 或宣传活动；
- 设计定价、销售页或付费转化实验；
- 为了营销效果改产品优先级。

一句判断：**工作自然产生的原始证据可以留下；只要需要专门制作、包装或发布，就进入 MKT 队列等待。**

## 5. WIP 与交替节奏

### 5.1 WIP 上限

- 单个 Agent 同一时刻只能执行一个任务。
- P 路线最多一个 active product milestone。
- MEM 路线最多一个 active study unit。
- 营销闸门前 MKT 没有 active deliverable，只有素材收集。
- HANDOFF 可以有候选项，但“被记录”不等于“已排期”。
- 多 Agent 并行只能服务同一个 active deliverable；若研究需要并行运行，必须使用隔离 snapshot，且不能让另一条产品改动污染冻结 wave。

### 5.2 营销闸门前的默认节奏

完成 §6 的 E-core 过渡里程碑前，按其中的静态依赖执行。此后默认按里程碑交替：

~~~text
一个产品里程碑
→ 一个有边界的记忆研究里程碑
→ 一个产品里程碑
→ 一个记忆研究里程碑
→ …
~~~

例外只有两种：

1. §6 的 MEM0、E1、E2 合并为一次 **E-core 原子研究里程碑**。它只能包含运行 E1/E2 所必需的协议冻结、harness/smoke、E1 和 E2，不得吸收项目工作指南 pilot、完整 Track A/B、论文或产品 schema；E2 结束后必须回到 P1。若达到预先冻结的成本/时间停止线或任一步被阻塞，立即停止 E-core，记录 HANDOFF，并回到用户已批准的产品 fallback；
2. 紧急中断按 §8 处理，结束后回到原节奏。

产品工作已准备好时，Agent 不得连续开启两个新的研究里程碑；研究工作已准备好时，也不得连续堆多个非阻断小功能逃避研究。

### 5.3 营销闸门开启后的默认节奏

营销只有同时满足以下条件才具备“可申请重开”的资格：

1. 预先冻结的 Track A 核心受控研究已经完成，而不是 smoke test 或内部 pilot；
2. Track B 真实客户端 Source × Target 已形成可复核的决策级结果；负结果或边界结果也算成果，但不得包装成胜出；
3. 原始数据、分析代码/口径、失败和限制可追溯；
4. 可披露数字已经进入 CASE_STUDY_LEDGER.md；
5. 用户明确说“重开营销”。

满足前四项仍不会自动开营销；第 5 项不可省。

重开后的默认里程碑节奏是：

~~~text
P → MEM → P → MKT → 重复
~~~

产品仍占一半里程碑，并且任何 MKT 项都不能连续执行两次，除非用户明确临时调整。

### 5.4 阻塞时如何切换

- P 被外部依赖、硬件或用户选择阻塞：写入 HANDOFF，可执行下一个已准备好的 MEM 单元；不得自行把另一个产品候选提到前面。
- MEM 被预算、样本、模型或伦理条件阻塞：写入 HANDOFF，立即回 P。
- MKT 被阻塞：记录后回 P；营销永不阻塞产品或研究。
- 阻塞解除后，回到被中断的路线；不能把临时绕行解释为永久重排。

| 7 | MEM | Track C 纵向研究、论文与复现 | Track A/B 结果支持继续；伦理、许可和数据保留已决定 |

这张表是 v1.0 的默认执行基线，不是允许 Agent 猜实现细节：

- 某项进入条件不满足时按 §5.4 处理；
- F3 的存储模型、F4 的平台先后等未决问题必须问用户；不得把平台先后误写成推翻“麦克风先、系统音频后”；
- 不得用一个大研究阶段把多个里程碑合并后长期占住产品线；
- 任何永久重排仍需修改本文件的明确许可。

### 6.9 F 批之后

产品不会停止。最后一个已批准产品里程碑完成时：

1. 汇总 HANDOFF 中尚未排期的产品候选；
2. 按用户影响、当前证据、依赖与工作量列出选择；
3. 明确说明选一个会推迟什么；
4. 由用户批准下一项 P milestone；
5. 继续遵守 P / MEM 交替。

Agent 不得因为“路线表走完了”宣告产品线结束，也不得一次把所有 HANDOFF 候选搬入长期方针。

## 7. 新任务、小功能与 HANDOFF 纪律

### 7.1 唯一收件箱

开发、测试、研究和真实使用中发现的以下内容一律进入最新 HANDOFF：

- 非阻断 bug；
- 小功能和 UI/UX 细节；
- 技术债；
- 新实验变量；
- 新竞品或论文带来的候选；
- 营销素材路径；
- 需要用户拍板的问题；
- 可能影响方针但尚未批准的建议。

不得把它们加入本文件；不得让 WORKPLAN 继续增长；不得新建另一份平行 backlog。

### 7.2 HANDOFF 新发现模板

~~~markdown
### DISCOVERED-YYYYMMDD-N · 标题

- 路线：P / MEM / MKT
- 类型：当前阻断 / 当前验收必要 / 非阻断 bug / 小功能 / 研究变量 / 素材 / 战略候选
- 来源：用户原话、代码位置、测试、真实运行或外部来源
- 证据：
- 影响：
- 与当前任务关系：
- 依赖：
- 建议：立即最小处理 / 候选等待 / 需要用户决定
- 验收标准：
- 严重度：P0 / P1 / P2 / P3
- 建议位置：只作建议，不等于批准
- 状态：captured / approved / active / blocked / awaiting-user-validation / completed / rejected
~~~

Agent 发现的事项默认是 captured。只有用户明确批准或它本来就是 WORKPLAN 中已批准的未完成项，才可成为 approved；记录本身没有执行授权。

Agent 可以把既有验收条件改写成可测试的检查项，但不得扩大其产品范围。若所谓“必要项”只来自 Agent 新写的 acceptance，而用户、active HANDOFF 或既有 WORKPLAN 之前没有这项要求，它仍是 captured；除 §8 的安全止损外，必须等待用户批准。

### 7.3 五类发现如何处理

| 类型 | 是否可当场做 | 处理 |
|---|---|---|
| 数据损坏、隐私/安全、失控付费、发布完整性 | 可以中断 | 先保护用户和证据，记 HANDOFF，做最小修复或停止 |
| 用户、active HANDOFF 或既有 WORKPLAN 在发现前已经定义的验收必要项 | 可以纳入当前范围 | 引用原验收条款，记录后只做满足它的最小改动 |
| 非阻断 bug / 小功能 / polish | 不可以 | 记 HANDOFF，继续当前任务 |
| 新战略、架构扩张、额外平台 | 不可以 | 记 HANDOFF，等待用户在里程碑闸门决定 |
| 营销想法或可包装内容 | 不可以制作 | 只保存自然产生的素材，进入 MKT 队列 |

### 7.4 禁止的插队理由

- 改动很小；
- 测试顺手能补；
- 和当前文件相邻；
- 可以让架构更漂亮；
- 以后可能需要；
- 竞品刚发布；
- Agent 已经想好了实现；
- 用户仅在讨论中提到；
- 旧 WORKPLAN 说某批可以“随时插”。

### 7.5 HANDOFF 控制体积

- 始终只有一份 active HANDOFF。
- 当前里程碑结束时，把完成事实、测试和回执写入 HANDOFF。
- 当 HANDOFF 承载的已完成历史明显压过下一窗所需信息时，新建日期版并归档旧版。
- 新版只带当前状态、唯一下一步、仍未解决的阻断和候选索引，不复制全部历史。
- 归档文件不再作为开工入口。

## 8. 允许临时中断的硬条件

只有以下情况可以绕过常规交替：

1. 可能丢失或损坏用户数据；
2. 隐私、权限、跨项目读取或非预期出网；
3. 自动调用可能反复花费用户额度；
4. 发布包、签名、公证、迁移或升级完整性失败；
5. 用户、active HANDOFF 或既有 WORKPLAN 已定义验收的直接阻断；
6. confirmatory 数据泄漏、条件污染或继续运行会让研究失效。

中断时必须：

- 停止扩大影响；
- 保存日志、原始数据或现场；
- 在 HANDOFF 标明被中断任务和恢复点；
- 只做最小安全处置；
- 处置后恢复原顺序，或因需要新权限而询问用户。

性能优化、代码整洁、视觉 polish、文档顺手更新和一般技术债不属于紧急中断。

## 9. 每个 Agent 的执行流程

### 9.1 开工

1. 读本文件；
2. 找首屏明确 active、未标 SUPERSEDED、取代关系最新的 HANDOFF，并确认它是否明确引用本文件；
3. 读当前任务对应的 WORKPLAN 小节；
4. 若涉及项目记忆产品设计，读 docs/DESIGN_PROJECT_MEMORY.md；
5. 若涉及 E 批、memory、benchmark 或论文，读 docs/AI_MEMORY_EXPERIMENT_PROTOCOL-2026-08-26.md；
6. 查代码和测试验证当前事实；
7. 查看 git status，保护用户已有改动；
8. 在动手前复述用户、active HANDOFF 或既有 WORKPLAN 已定义的范围与验收，并写明不做事项；可增加验证细节，不得自行扩大产品范围。

### 9.2 执行中

- 一次只推进当前里程碑；
- 发现新事项按 §7 记录，不扩 scope；
- 当前用户指令优先，但区分一次性任务和永久改方针；
- 研究按 frozen protocol；产品按当前事实；营销只收 raw evidence；
- 不用模型自述替代 tool trace、代码或真实运行证据。

### 9.3 收尾

必须完成：

- 与风险相称的测试或人工验收说明；
- git diff / status 检查；
- HANDOFF 更新：变更、验证、未解决、新发现、素材、唯一下一步；
- 既有 WORKPLAN 项完成时按原规则移除/归档，不能往里加入新任务；
- 明确下一窗读哪些小节；
- 分开记录 commit、build、换装、发布、push 和真实手指验收；其中一个完成不能冒充其他步骤；
- 确认本文件没有因本次日常收尾出现在新增 diff 中；
- 不修改本文件，除非本轮拥有 §3.1 的明确许可。

| 文档 | 回答的问题 | 使用方式 | 禁止误读 |

- 动态状态听最新 HANDOFF；
- 已实现事实查代码和测试。
